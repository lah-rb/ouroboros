# OCR lane: can the figtext treatment be repeated? — Phase 0

**Date:** 2026-08-29 · **Machine:** RTX 3090 (CUDA0) + RTX 3060 (CUDA1), paddle
pinned to CUDA1 · **Mission:** stopped throughout · **Corpus:**
`~/corpora/ouroboros-spectra`, 626 papers pending OCR

## The question

The figtext campaign collapsed a ~2-week job into ~2 days (168 → 546 figs/h,
3.3×) with two moves: server-side **batched vision** (N sequences in one
`llama_context`, shared weight reads) and **lane multiplication** (1 → 4
`figtext*` worker lanes). OCR is the scraper's other visual half. Does the
same treatment apply?

Phase 0 was designed to answer that **before** any product code, with the
verdict rules written down first. Both headline levers were refuted. The
plan self-terminated on its own evidence, which is what it was for.

## Pre-registered predictions (written before any cell ran)

| # | Prediction | Outcome |
|---|---|---|
| 1 | OCR is encode-dominated; decode share < 40 %, likely < 30 % | **Direction right, mechanism wrong.** Decode is 12.8 %, but encode is only 7.1 % — the request is dominated by neither. |
| 2 | Pool width 2 → 4 buys ~11 % (read off the synthetic pool curve) | **Refuted.** Width buys nothing; 2 is marginally the best of 2/4/8. |
| 3 | `(4 × 16384)` costs exactly what `(2 × 32768)` costs | **Confirmed** — both preflight at 2.09 GB, byte-identical. |

## Method

Hand-made inputs were tried first and thrown away: a hand-cropped page band
is ~400 k px and paddle **degenerates** on it ("The text in the image is the
last part of the image…"), while real paddlex crops are single text **lines**
— 887×32, 815×25 px, 15–60× smaller — which transcribe cleanly. A stage split
measured on the fabricated shape would have been a confident number about a
request OCR never makes.

Instead `llmvp/probe_ocr_proxy.py` was placed between `extract_batch.py` and
the server (`OUROBOROS_LLMVP_URL`), and the **real tool ran over real PDFs
from the pending queue**. Every request's crop area, output tokens, wall time
and in-flight concurrency were recorded. Output length and crop area vary
naturally across crops, so the production trace carries the regression
variance an artificial sweep would have had to manufacture.

- `llmvp/probe_ocr_analyze.py` — fits `wall = a + b·tokens + c·area`
- `llmvp/probe_ocr_sweep.py` — restarts the server per geometry, runs the
  tool, keeps the tool's own numeric/span recall per cell
- `llmvp/probe_ocr_floor.py` — decomposes the per-request floor
- `llmvp/configs/experiments/paddle-ocr-stage-probe.yaml` — paddle standing
  alone with the OpenAI shim on (production reaches it as a hot *secondary*
  on muse's server, so its own config needs no shim)

## P0a — where an OCR request's time goes

Fit over **170 queue-free rows** (concurrency == 1) of real production traffic:

| stage | cost at the median request | share |
|---|---|---|
| fixed | 166.8 ms | **80.1 %** |
| encode (867 ms/Mpx) | 14.7 ms | 7.1 % |
| decode (1.52 ms/tok → 657 tok/s) | 26.6 ms | **12.8 %** |

Independent check: observed p10 wall is 168 ms against a fitted intercept of
167 ms — the cheapest real request *is* the floor, so the intercept is not an
artefact of the fit.

Direct decomposition of that floor (`max_tokens=8`, n=12–15 each):

| arm | area | median |
|---|---|---|
| blank 32×32 | 1,024 px | **91.3 ms** |
| real crop | 28,160 px | 115.7 ms |
| full page | 2.39 Mpx | 1190.5 ms |

→ marginal encode 454 ms/Mpx; a real crop pays ~24 ms for its own size.

Splitting the 92 ms floor further:

| component | cost | share |
|---|---|---|
| transport + JSON + base64 intake | **0.8 ms** | 1 % |
| prompt prefill (112 tok @ 0.054 ms/tok) | ~6 ms | 7 % |
| image encode (1,024 px) | ~0.5 ms | 1 % |
| decode (3–5 tok) | ~6 ms | 7 % |
| **unaccounted per-request overhead** | **~79 ms** | **86 %** |

`vision.decode_ms` accounts for 99 % of client wall, so the cost is entirely
server-side, between the vision-instance checkout and the end of
`create_chat_completion`. It scales with **nothing measurable**: not image
area, not output length, not prompt length, and not `vision_n_ctx` (per-cell
p05 floors: 179.7 / 195.6 / 205.6 ms at 32768 / 16384 / 8192 — flat, so the
per-request context clear is not the cost either).

## P0b — pool width sweep

Identical workload (6 papers × 4 pages) across the iso-memory ladder:

| cell | pool | n_ctx | par | wall s | **pg/min** | numeric | span | max repeat |
|---|---|---|---|---|---|---|---|---|
| uncontended control | 2 | 32768 | 1 | 69.4 | 10.38 | 0.822 | 0.863 | 2 |
| **production today** | 2 | 32768 | 4 | 127.9 | **11.26** | 0.674 | 0.819 | 15 |
| width-4 iso-mem | 4 | 16384 | 4 | 138.9 | 10.37 | 0.674 | 0.813 | 32 |
| width-8 iso-mem | 8 | 8192 | 4 | 133.1 | 10.82 | 0.674 | 0.792 | 2 |

(The control ran 3 papers, not 6 — it exists only to supply queue-free rows,
and its quality column is **not** comparable to the rest.)

- **Width buys nothing.** 2 → 4 → 8 contexts moves 11.26 → 10.37 → 10.82
  pg/min. Today's width of 2 is marginally the best of the three.
- **4-wide fan-out barely beats serial**: 11.26 vs 10.38 pg/min, **+8.5 %**
  for 4× the offered load.
- **Quality is insensitive to the window**: numeric recall is *identical*
  (0.6744) at 32768, 16384 and 8192 on the same workload. `vision_n_ctx` is
  ~4× oversized — which would matter if width were useful. It is not.

Per-request wall against in-flight concurrency (pool 2) shows where the time
goes instead: 1 → 190 ms, 2 → 295, 3 → 537, 4 → 895. paddlex fans 4-wide by
default (`vl_rec_max_concurrency`), so most requests queue — but widening the
pool to absorb them does not convert into throughput, because the cost being
queued for does not parallelize.

## Verdicts

| Phase | Rule | Verdict |
|---|---|---|
| **4 — M-RoPE batched path** | decode share < 30 % → do not build | **DEAD.** 12.8 %. Batching multiplexes decode and *serializes* encode behind `MtmdEncoder`'s process-wide lock, while each pool instance owns its own mtmd context (`llama_multimodal.py:221`) and encodes in parallel. At this mix batching is not merely weaker — it is the wrong architecture. ~1.5 days not spent. |
| **2 — server widening** | width must pay | **DEAD.** Width 2/4/8 is flat. Do not raise `vision_pool_size`, do not raise `DEFAULT_LANE_MAX_INFLIGHT["paddle"]`, do not add `ocr2`/`ocr3` lanes — a lane that only deepens a queue is noise in the telemetry. |
| **1 — shared drain-lane module** | independent of the above | **PROCEED** (done; see below). |
| **3 — tool-side** | reframed | The lever is the **~92 ms per-request floor**, not page pipelining. At ~30 crops/page that is ~3 s of a ~5.7 s page. |

## What the lever actually is

OCR throughput is bound by a **fixed per-request serving cost**, not by
vision capacity. Everything that scales — encode, decode, transport, prefill
— sums to ~14 % of a crop request. The remaining ~79 ms is paid once per
request regardless of what the request contains, and it does not parallelize
across pool contexts.

Two directions follow, in this order:

1. **Find the 79 ms.** It sits between the vision-instance checkout and the
   end of `create_chat_completion`. A `py-spy` profile of the server under a
   crop stream would localize it in minutes (py-spy is not installed; install
   with `uv pip install`, never a bare `uv sync`). Leading suspect: the
   `llama_set_causal_attn(false/true)` bracket around the image decode in
   `mtmd_helper_eval_chunk_single` — toggling context-global causal attention
   once per request is exactly the kind of thing that forces a graph re-plan.
   Cheap to test: compare a model whose handler takes the non-causal path
   against one that does not.
2. **Send fewer, bigger requests.** The floor is per REQUEST, so ~30 line
   crops per page pay it ~30 times. Batching crops per call would amortize it
   — but the decomposition is paddlex's, not ours, so this is a
   `vl_rec_*` / pipeline question rather than a serving one.

## Corrections to the record

- **"Fork-level M-RoPE batch support" was too pessimistic.** The atomic
  installer `mtmd_helper_decode_image_chunk` already takes an explicit
  `seq_id` and already works into a shared context. The only refusal is an
  accounting guard at `llmvp/inference/vision_batched.py:404-416`
  (`delta != seg.n_tokens`): under M-RoPE an image advances `n_past` by
  `mtmd_input_chunk_get_n_pos()` = `max(t,h,w)`, not by `n_tokens`. That is
  the R3 "cell debt" the batched-vision plan anticipated, and it collapsed to
  nothing for muse. It is our Python, no rebuild. **Recorded so nobody
  re-derives the pessimistic version — not because it should be built.**
- **The `vision_pool_size: 4` OOM cause is gone.** The preflight governor
  counted ONE vision context instead of `vision_pool_size`; that is fixed
  (`llama_cpp_backend.py:4012-4020`). The config header still explains the
  4 → 2 walk-down as if the hazard stood. It does not — but width is
  worthless anyway, so leave the value at 2 and fix only the comment.
- **`llmvp/configs/experiments/paddle-ocr-vl-probe.yaml` has a stale macOS
  path** (`/Users/lah-rb/.lmstudio/...`). Unrelated to this work, unused, and
  the exact cross-machine-port failure mode that fails silently.

## Phase 1 — shipped alongside

`agent/actions/drain_lane.py` holds what three drains had each grown their own
copy of: the call-time env budget reader, the `ClaimSet` with a release-on-any-
exit scope, the `decline()` that satisfies `_did_work`'s `reason` contract by
construction, `select_cost_bounded()` (greedy, with the never-starve escape),
`server_alive()` and `park()`. Both figtext and OCR are migrated onto it in
one change; `select_ocr_batch`/`release_ocr_keys`/`_OCR_CLAIMS` keep their
names and shapes so `acquire_overlap_actions` and the existing tests are
untouched.

The one behaviour change: **OCR rounds are now bounded by PAGES as well as
papers** (`OUROBOROS_OCR_DRAIN_PAGES`, default 120 ≈ today's typical 4 × ~33).
Paper count alone let round duration swing ~20× against one fixed
`EXTRACT_TIMEOUT_S`, and only the long rounds hit it and lose their tail to
`unjudged`. `max_pdfs` stays a hard ceiling, so rounds can only get smaller or
more even than what already ran.

## Reproducing

```bash
# paddle alone, shim on, mission stopped
printf 'paddle-ocr-stage-probe\n' > llmvp/active_config.txt
LD_LIBRARY_PATH=$HOME/cuda-libs/nvidia/cublas/lib:$HOME/cuda-libs/nvidia/cuda_runtime/lib \
  setsid nohup llmvp/.venv/bin/python llmvp/api/main.py > ~/tmp/llmvp_probe.log 2>&1 & disown

llmvp/.venv/bin/python llmvp/probe_ocr_proxy.py --port 8010 &   # then point the tool at :8010
llmvp/.venv/bin/python llmvp/probe_ocr_sweep.py                 # the 4 cells
llmvp/.venv/bin/python llmvp/probe_ocr_floor.py                 # the floor decomposition
llmvp/.venv/bin/python llmvp/probe_ocr_analyze.py <wire.jsonl>  # the stage split
```

Data: `llmvp/probe_out/ocr_sweep.jsonl`, `ocr_floor.jsonl`, `ocr_wire_*.jsonl`.

**Gotcha worth keeping:** the sweep driver `os.remove`s the wire log between
cells, but the proxy holds the open handle and keeps writing to the unlinked
inode — the per-cell files come out empty. The data is recoverable live from
`/proc/<proxy-pid>/fd/N`, and cells split cleanly on the `srv_<epoch>.log`
timestamps. Fix is to record an offset rather than unlink.
