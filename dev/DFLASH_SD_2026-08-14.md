# muse dflash speculative decoding on M1 Ultra: NET NEGATIVE

*Measured 2026-08-14. Probe: `dev/dflash_sd_probe.sh`. llama-server build
10360 (48d22e295), muse-glimmer-30B kquant-dynamic + dflash-kquant, greedy
(temp 0 / top_k 1), batch 1, n_predict 200, `-ngl 99 -ngld 99`.*

## Result

| arm | tok/s | vs baseline | draft acceptance | mean accepted run |
|---|---|---|---|---|
| baseline (no draft) | **20.74** | — | — | — |
| dflash, n_max 3 (default) | 18.19 | **−12%** | 0.381 (106/278) | 2.14 |
| dflash, n_max 8 | 10.40 | **−50%** | 0.185 (118/639) | 2.46 |
| dflash, n_max 16 | 10.59 | **−49%** | 0.108 (122/1125) | 2.58 |

Speculative decoding genuinely ENGAGED in every draft arm — the acceptance
statistics prove it, and the default n_max=3 is already the best case. Longer
drafts are catastrophically worse: acceptance collapses 0.38 → 0.11 while the
verify batch widens, so the machine burns compute on tokens it throws away.

**The published 1.5x does not transfer.** The meta-models card reports M4 Max
23.7 → 37.8 tok/s. This is an M1 Ultra: ~800 GB/s of bandwidth against
relatively less compute per unit of it. Speculative decoding trades
bandwidth-bound sequential decode for compute-bound parallel verify — the
machine with more bandwidth and less compute is exactly where that trade pays
least. Predicted before measuring, and the sweep confirms it.

Nothing here says dflash is bad. It says dflash is bad *on this hardware*, and
the 3.1x on an RTX 5090 is the same physics pointing the other way. **Re-run
this probe on the 3090/3060 rig before assuming either result.**

## Three traps, any of which fakes a verdict

**1. `--spec-type` defaults to `none`.** The model card's command is
`-md <drafter> -ngld 99`, which in this build loads the drafter, occupies its
~1.6 GB, and does NOTHING. Measured: 20.78 tok/s on all three arms,
byte-identical to baseline. Without `--spec-type draft-dflash` the feature is
inert and looks like "no speedup".

**2. Unified KV cache silently disables `-md`** (llama.cpp issue #25345,
regression from build a410713, 2026-07-05, still open). Our muse config sets
`kv_unified: true`. Worse, the documented workaround does not work: with
`--no-kv-unified` the log STILL prints `kv_unified = 'true'` — the secondary
flag-handling bug the issue reports. In this measurement it did not matter,
because `--spec-type` engaged SD regardless, but on a build where it does
matter the failure is silent.

**3. Readiness is HTTP 200, not a connection.** llama-server binds the port
immediately and answers `/health` with 503 while an 18 GB model loads. A
`curl && break` loop returns 0 on that 503, so the first version of this probe
fired every request mid-load and reported 0.00 tok/s across the board — which
reads as a result rather than a broken harness.

Any of these three produces a confident, wrong number. The probe checks for
`n_drafted`/`n_accept` in every arm for exactly this reason: an arm with no
acceptance statistics proved nothing, however plausible its tok/s looks.

## What it means for LLMVP

**Nothing to build, and that is the useful part.** LLMVP serves muse
in-process through llama-cpp-python, whose only `LlamaDraftModel`
implementations are `LlamaNGramMapDecoding` and `LlamaPromptLookupDecoding` —
n-gram heuristics, not model drafting. `nm -gU libllama.dylib` exports zero
speculative symbols, because in llama.cpp that logic lives in `common/`, not
the public C API.

So adopting dflash would have meant serving muse through llama-server and
giving up the seq-band KV machinery, sessions, personas, reasoning head-swap
and the batched engine. On this hardware that trade would have bought −12%.

Also, independently: `--mmproj` + `--model-draft` terminates the server
(issue #19712). Muse is our vision model, so SD and vision cannot share an
instance even where SD helps.

## Status

CLOSED for M1 Ultra. Re-open only with new hardware or a materially different
drafter — and re-run `dev/dflash_sd_probe.sh` rather than trusting a card.
